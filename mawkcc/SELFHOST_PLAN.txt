mawkcc Self-Hosting Porting Retrospective
=========================================

This file is a reflection on how the self-hosting port was done. For the
current self-hosted compiler state, build scripts, and verification commands,
see `SELFHOST.txt`.


Starting Point
--------------

The project began with `cc.awk` as the working compiler. The main risk in
porting was not semantic behavior alone, but preserving exact output bytes:
ELF headers, section/program headers, instruction order, string placement,
data layout, relocation ordering, and patching behavior all had to remain
stable.

Because of that, the first implementation step was to create
`mawkcc_orig.c` as a close ANSI C port of `cc.awk`. This was deliberately a
transliteration rather than a redesign. It gave the project a readable C
reference implementation while keeping `cc.awk` as the original byte-level
authority.


Parity First
------------

The port was driven by parity tests. Each meaningful step had to preserve
bit-identical output between:

- `cc.awk`
- `mawkcc_orig.c`
- the split/self-hosted compiler path
- the GCC-built cross-check path

This discipline avoided a common self-hosting failure mode: making a compiler
that appears to work but has silently drifted in output format or ABI details.

The parity harness eventually grew to cover both executable output and ELF
relocatable object output. It also records build commands in `artifacts` so
the self-hosted object build path can be audited directly.


The Intermediate Split
----------------------

The compiler was temporarily split into:

- `mawkcc_self.c`: code intended to fit the restricted mawkcc dialect
- `mawkcc_ansi.c`: host-side ANSI C code left behind during migration

That split made the port incremental. Code could move from the ANSI side into
the self-hosted dialect in small pieces while the combined compiler continued
to emit byte-identical output.

The important rule during this stage was that `mawkcc_ansi.c` should shrink
only when parity still passed. It was not acceptable to hide compiler logic in
new support files just to make the ANSI file empty.


Dialect Constraints
-------------------

The mawkcc dialect was intentionally not extended during the port. That shaped
several implementation choices:

- token constants became initialized global variables rather than C enums or
  preprocessor definitions
- struct-like records are accessed through explicit getter and setter helpers
- global arrays are represented through allocated pointer-backed tables
- helper names stay short where the dialect makes verbose code costly

The self-hosted source also had to remain readable and auditable. Avoiding
magic numbers was more important than making the code look like normal C.


Object Support
--------------

Self-hosting required better object-file support than the original executable
only path. mawkcc was updated to emit ELF32/i386 relocatable objects that can
be linked by GCC.

That work included:

- emitting symbols and relocations for mawkcc functions and globals
- allowing generated object code to call functions defined in C
- allowing generated object code to access integer variables defined by C
- keeping `cc.awk`, `mawkcc_orig.c`, and `mawkcc_self.c` object output
  byte-identical

Those tests were important because self-hosting is not just "can emit an
executable"; it also needs a trustworthy object/link path.


Executable Layout
-----------------

The early compiler executable path used a fixed code page and a fixed data
page. That became an arbitrary limit once `mawkcc_self.c` grew large enough to
build the compiler.

The final executable emitter records absolute data references while generating
code, then computes the final data address after code size is known. It patches
those references just before writing the ELF image. This removed the manual
code-page setting while preserving byte identity across implementations.


End State
---------

After the migration, all compiler logic had moved into `mawkcc_self.c`.
`mawkcc_ansi.c` became an empty placeholder and was then removed from the
tree.

The final verification model is:

- `scripts/run-tests.sh` runs the build verifier first
- the build verifier confirms the awk, self-hosted, reference-C, and GCC
  build routes emit identical mawkcc binaries
- each emitted mawkcc binary must rebuild itself identically
- the normal tests then check runtime behavior, object linking, external C
  calls, external C integer variables, and parity on example programs

The result is a self-hosted compiler whose active implementation is
`mawkcc_self.c`, with `cc.awk` and `mawkcc_orig.c` retained as reference and
regression anchors.
