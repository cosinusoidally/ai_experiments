mawkcc Dialect Specification
===========================

Overview
--------

`mawkcc` compiles a small language into 32-bit x86 Linux ELF binaries.
The compiler is implemented in `mawk`.

The source language is designed so that its function-definition and
function-body syntax can be treated as a shared subset across C,
JavaScript, and `awk`, with these conventions:

- `function` can be treated as a C type name such as `int`
- function parameters are implicit 32-bit integers
- operations are expressed as function calls rather than infix operators

This document describes the language currently implemented by
`cc.awk`, not a future or intended language.

The self-hosted compiler source also follows the stricter
C/JavaScript/awk-compatible source shape documented in
`BOOTSTRAP_DIALECT.txt`.


Execution Model
---------------

- Target: Linux ELF32, Intel i386
- Entry point: `_start` generated by the compiler
- Startup behavior: `_start` calls `main()` and exits the process using
  `main`'s return value as the process exit status
- Integer model: signed 32-bit integer operations at the machine-code
  level
- Calling convention: compiler-defined stack-based convention using
  `call`, `ret`, and an `ebp` frame

Startup arguments:

- `_start` calls `main(argc, argv)`
- `argc` is the process argument count
- `argv` is a pointer to the first element of the argument-vector array
- `argv` therefore behaves like a pointer to an array of 32-bit pointers
- the address of `argv[i]` is `add(argv, mul(i, 4))`
- the pointer value of `argv[i]` is `ri32(add(argv, mul(i, 4)))`


Translation Unit Structure
--------------------------

A source file is a sequence of:

- global declarations
- function definitions

Globals must appear before any function definition.

Accepted top-level forms:

- `var name;`
- `function name(arg1, arg2, ...) { ... }`

Rejected top-level forms include:

- initialized globals such as `var x = 1;`
- statements outside functions
- nested functions


Lexical Rules
-------------

Identifiers:

- first character: `A-Z`, `a-z`, or `_`
- later characters: `A-Z`, `a-z`, `0-9`, or `_`

Numbers:

- decimal integer literals only
- no hexadecimal, octal, binary, or floating-point literals

Comments:

- `// ...`
- `/* ... */`

Punctuation tokens:

- `(` `)` `{` `}` `;` `,` `=`

Reserved words:

- `function`
- `var`
- `return`
- `if`
- `else`
- `while`
- `break`

String literals:

- double-quoted only
- currently supported escapes:
  `\"`, `\\`, `\n`, `\t`, `\r`, `\0`

There are no character literals.


Globals
-------

Syntax:

- `var name;`

Rules:

- globals are file-scope only
- globals cannot be initialized at declaration time
- globals must be declared before any function definition
- each global occupies 4 bytes
- globals are stored in the writable static data area

Example:

    var counter;
    var fd;

Invalid:

    var counter = 1;


Functions
---------

Syntax:

    function name(arg1, arg2, arg3) {
        ...
    }

Rules:

- parameters are implicit 32-bit integers
- duplicate function names are rejected
- duplicate parameter names are rejected
- function overloading is not supported
- `main` must exist

Calls:

- user-defined functions may call previously defined or later defined
  functions
- call arity must match definition arity exactly

Default return:

- if execution reaches the end of a function body without a `return`,
  the compiler emits `return 0`


Statements
----------

The currently supported statements are:

- block statement
- expression statement
- `return expr;`
- `if (expr) stmt`
- `if (expr) stmt else stmt`
- `else if` as a chained `else` followed by `if`
- `while (expr) stmt`
- `break;`

Block statement:

    {
        stmt1;
        stmt2;
    }

Restrictions:

- `break;` is only valid inside `while`
- `continue` is not supported
- local variable declarations are not supported


Expressions
-----------

Supported expression forms:

- decimal integer literal
- parameter reference
- global reference
- parenthesized expression
- builtin function call
- user-defined function call
- assignment to a global
- assignment to a parameter
- `mks("...")` string materialization

Examples:

    42
    answer
    add(1, 2)
    times(6, 7)
    answer = 42
    wi32(ptr, 99)

Assignment:

- only globals and parameters may appear on the left-hand side
- assignment is an expression statement in practice
- assignment leaves the assigned value in `eax` as part of codegen, but
  the language should not rely on chaining behavior

Unsupported expression features:

- infix arithmetic operators such as `+` or `*`
- logical operators such as `&&` or `||`
- comparison operators such as `<` or `==`
- local variable assignment
- arrays
- struct access
- pointers as syntax
- unary operators in source syntax


Control Flow Semantics
----------------------

Conditions:

- a condition expression is false when it evaluates to `0`
- any non-zero value is treated as true

`if` example:

    if (eq(x, 0)) {
        return 1;
    } else if (lt(x, 0)) {
        return 2;
    } else {
        return 3;
    }

`while` example:

    while (lt(i, 10)) {
        if (eq(i, 6)) {
            break;
        }
        i = add(i, 1);
    }


Builtins
--------

All operators and most runtime services are exposed as builtins.

Unary builtins:

- `neg(x)`
- `not(x)`
- `ri32(addr)`
- `ri8(addr)`
- `brk(n)`
- `close(fd)`
- `mks("...")`
- `mkC("x")`

Binary builtins:

- `add(a, b)`
- `sub(a, b)`
- `mul(a, b)`
- `div(a, b)`
- `mod(a, b)`
- `eq(a, b)`
- `ne(a, b)`
- `lt(a, b)`
- `le(a, b)`
- `gt(a, b)`
- `ge(a, b)`
- `and(a, b)`
- `or(a, b)`
- `xor(a, b)`
- `shl(a, b)`
- `shr(a, b)`
- `wi32(addr, value)`
- `wi8(addr, value)`

Ternary builtins:

- `open(path_addr, flags, mode)`
- `read(fd, buf_addr, count)`
- `write(fd, buf_addr, count)`


Arithmetic and Comparison Builtins
----------------------------------

`add(a, b)`

- returns `a + b`

`sub(a, b)`

- returns `a - b`

`mul(a, b)`

- returns signed `a * b`

`div(a, b)`

- returns signed `a / b`
- division by zero is not checked by the language

`mod(a, b)`

- returns signed `a % b`
- division by zero is not checked by the language

Comparison builtins return:

- `1` for true
- `0` for false

Comparison set:

- `eq(a, b)`
- `ne(a, b)`
- `lt(a, b)`
- `le(a, b)`
- `gt(a, b)`
- `ge(a, b)`


Bitwise and Boolean-Like Builtins
---------------------------------

`and(a, b)`

- bitwise AND

`or(a, b)`

- bitwise OR

`xor(a, b)`

- bitwise XOR

`shl(a, b)`

- left shift

`shr(a, b)`

- right shift

`neg(x)`

- arithmetic negation

`not(x)`

- logical not
- returns `1` when `x == 0`
- returns `0` otherwise


Memory Model
------------

Memory builtins operate on absolute addresses.

Static writable data area:

- globals are placed at fixed absolute addresses in the ELF image
- runtime bookkeeping such as the current heap break is also stored
  there

Heap:

- `brk(n)` allocates `n` bytes from the process break
- on first use, `brk(0)` is used internally to fetch the current break
- on success, `brk(n)` returns the previous heap pointer
- on failure, `brk(n)` returns `0`

Memory access builtins:

`ri32(addr)`

- reads a 32-bit value from `addr`

`wi32(addr, value)`

- writes a 32-bit value to `addr`

`ri8(addr)`

- reads one byte from `addr`
- returns it zero-extended to 32 bits

`wi8(addr, value)`

- writes the low 8 bits of `value` to `addr`
- returns the written byte value zero-extended in the generated code

No bounds checking is performed.


File I/O
--------

File I/O is thin syscall-level access.

`open(path_addr, flags, mode)`

- Linux i386 `open` syscall
- `path_addr` must point to a NUL-terminated byte string in memory
- returns a file descriptor on success
- returns a negative error code on failure, as per raw syscalls

`read(fd, buf_addr, count)`

- Linux i386 `read` syscall
- reads up to `count` bytes into `buf_addr`
- returns number of bytes read or negative error code

`write(fd, buf_addr, count)`

- Linux i386 `write` syscall
- writes `count` bytes from `buf_addr`
- returns number of bytes written or negative error code

`close(fd)`

- Linux i386 `close` syscall
- returns syscall result

The language does not provide:

- string literals
- symbolic open flags
- errno decoding
- buffered streams

Therefore paths and buffers must be built manually in memory, usually
with `brk` plus `wi8`, or with `mks("...")` for static NUL-terminated
strings.


Strings
-------

Strings are introduced through `mks("...")`.

Semantics:

- the argument must be a string literal
- the compiler materializes a NUL-terminated byte string in the program
  data area
- the expression evaluates to the absolute address of that string

Example:

    path = mks("artifacts/io42.dat");

In the current native compiler implementation, `mks` returns the
address of compiler-emitted static string data.

Single-byte constants are introduced through `mkC("x")`.

Semantics:

- the argument must be a string literal
- the expression evaluates to the first byte of that string literal
- it is intended for readable character constants in the self compiler


Name Resolution
---------------

Identifier lookup inside functions works as follows:

1. assignment target: only a global may appear before `=`
2. function call: an identifier followed by `(...)`
3. parameter reference
4. global reference

If an identifier is not found in those categories, compilation fails.


Examples
--------

Global assignment:

    var answer;

    function main() {
        answer = 42;
        return answer;
    }

Function call:

    function times(a, b) {
        return mul(a, b);
    }

    function main() {
        return times(6, 7);
    }

Loop with break:

    var i;

    function main() {
        i = 0;
        while (lt(i, 10)) {
            if (eq(i, 6)) {
                break;
            }
            i = add(i, 1);
        }
        return i;
    }

Heap and memory:

    var p;

    function main() {
        p = brk(4);
        wi32(p, 42);
        return ri32(p);
    }


Current Restrictions
--------------------

Not supported:

- local variables
- local declarations
- initialized globals
- `continue`
- string literals
- character literals
- arrays
- structs
- pointers as syntax
- preprocessing
- separate compilation
- native assembler or linker integration

Source is also intentionally restricted in style:

- no infix operators in expressions
- no declarations inside blocks
- no implicit coercion model beyond raw machine behavior


Simulating Locals
-----------------

The compiler does not implement true local variables, but bootstrap
source may simulate them using extra parameters.

Convention:

1. if a logical function `foo` needs locals, implement its body in a
   worker function named `foo_`
2. `foo_` takes:
   real parameters first, then one parameter slot for each simulated
   local
3. the public wrapper `foo(...)` calls `foo_(..., 0, 0, ...)`
4. inside `foo_`, those extra parameters are treated as mutable local
   slots by source convention

Example with two simulated locals:

    function foo_(a, b, tmp1, tmp2) {
        return add(tmp1, tmp2);
    }

    function foo(a, b) {
        return foo_(a, b, 0, 0);
    }

Important limitation:

- this is only a source-level convention
- true local declarations still do not exist
- the convention reuses mutable parameter slots rather than introducing
  a separate local storage class

In practice, this convention is useful for structuring bootstrap code
around helper parameters and wrapper functions, but full local-variable
behavior still requires explicit declaration support.


Portability Notes
-----------------

The compiler implementation targets `mawk`, but mostly stays close to
portable `awk` style.

The generated binaries are specific to:

- Linux
- 32-bit x86
- `int 0x80` syscall ABI

They are not portable to:

- x86-64-only execution environments without 32-bit compatibility
- non-Linux systems
- non-x86 systems


Status
------

This dialect is evolving alongside the bootstrap effort. This file
describes the current implemented behavior of the repository at the time
it was written.
